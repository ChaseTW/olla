# 屏方根主網站｜V1 資訊架構與內容分層

版本：1.0-draft  
規劃日期：2026-09-20  
狀態：第一版實作依據；不代表內容已取得公開核准  
適用範圍：品牌主站 V1、既有活動頁共存、V1.1 地方筆記與 Dokki 邊界

## 1. 本版決策

V1 先完成可獨立閱讀的品牌主站，沿用現有 Cloudflare Pages 靜態部署，不建立第二套 CMS，也不以後端服務阻塞上線。

- 首頁維持精煉，只負責建立整體認識與導向，不展開所有細節。
- V1 上線範圍包含首頁、關於我們、合作方式、合作案例、聯絡，以及經核准的案例內頁。
- 「地方筆記」V1 不上線：不出現在主導覽、首頁、footer、sitemap，也不部署試稿頁面。
- 既有「順事・芒種」活動頁原網址與功能完整保留。
- V1 內容先採靜態檔案；Dokki 是品牌知識與決策主檔，但不是瀏覽器端的即時資料 API。
- 未核准的品牌事實、案例成果、照片、人物、合作夥伴、聯絡方式或概念文案不得因版面需要而補寫成正式內容。

## 2. V1 的使用者任務

初次造訪者應能依序回答四個問題：

1. 屏方根是誰，從什麼地方與觀點出發？
2. 可以和屏方根一起做什麼？
3. 過去如何實際工作，有哪些可被理解的案例？
4. 若有合作需求，下一步怎麼聯絡？

網站是品牌與工作的公開入口，不是把 Dokki 內所有研究、會議與資料完整攤開。每一頁只承擔自己的閱讀任務，詳細內容不回填首頁。

## 3. V1 路由與發布狀態

| 路由 | 頁面責任 | V1 技術狀態 | 正式發布條件 |
| --- | --- | --- | --- |
| `/` | 品牌定位、屏東出發的觀點、合作方向、精選案例與下一步 | 納入 | 首屏文案、精選案例與影像均獲核准 |
| `/about/` | 品牌緣起、為何在屏東、工作觀點、團隊／角色與方法基礎 | 納入 | 品牌事實、人物與照片獲核准 |
| `/services/` | 合作情境、工作範圍、合作流程、交付邊界與必要 FAQ | 納入 | 服務描述與承諾範圍獲核准 |
| `/work/` | 合作案例索引；說明案例性質與屏方根角色 | 納入 | 至少有一則可公開案例；只列核准項目 |
| `/work/[slug]/` | 單一案例的背景、需求、判斷、過程、角色、成果與回顧 | 條件納入 | 該案例的名稱、角色、成果、夥伴、圖片及授權逐項核准 |
| `/contact/` | 正式聯絡入口、合作前需提供的基本資訊、資料用途與回覆安排 | 納入 | 至少有一個已驗證、可實際收件的聯絡管道 |
| `/events/mangzhong-2026-0605/` | 既有活動頁 | 原樣保留 | 不改網址、不破壞素材、互動、報名連結與 SEO 結構 |
| `/journal/`、`/journal/[slug]/` | 地方筆記索引與文章 | V1 不部署 | 延至 V1.1；V1 導覽與 sitemap 不得先放空入口 |

目前設計候選包中的 `puremosa`、`gift`、`mangzhong`、`erfeng` 等案例頁，只是技術與編排候選。slug、名稱或內容存在於概念稿，不等於已獲正式發布授權。未通過核准的案例應從 production 輸出移除，而不是以占位內容補滿或只靠 `noindex` 隱藏。

## 4. 全站導覽

### 4.1 主要導覽

建議固定為：

1. 首頁（品牌標誌連回 `/`，不必重複顯示「首頁」文字）
2. 合作案例 `/work/`
3. 合作方式 `/services/`
4. 關於我們 `/about/`
5. 主要行動：談合作 `/contact/`

V1 不顯示「地方筆記」。既有活動頁不必成為常駐主導覽項目；如內容關聯成立，可由首頁精選或已核准案例提供情境式連結。

### 4.2 頁尾導覽

頁尾至少提供主要頁面、正式聯絡方式、必要法律／隱私資訊與版權資訊。不得放入 Dokki、設計預覽、內部規範、測試環境或未部署的 Journal 連結。

### 4.3 返回與交叉閱讀

- 案例內頁要有返回案例索引的明確路徑。
- 案例可連至合作方式或聯絡頁，但不複製完整服務與表單內容。
- 活動頁維持既有獨立體驗；任何新增返回品牌站的連結都需另行回歸測試。

## 5. 頁面責任與內容層級

### 5.1 首頁：精煉的全站入口

首頁使用「共作長桌」的敘事精神，但內容層級必須克制。建議順序如下：

1. **品牌首屏**：一個核心主張、短定位與一個主要行動。
2. **地方觀點**：用一段經核准的文字交代屏東如何影響工作的觀看方式。
3. **合作摘要**：簡述可合作的情境，導向 `/services/`。
4. **精選案例**：只選 2–4 則已核准內容，導向 `/work/` 或案例內頁。
5. **關於摘要**：讓讀者理解品牌角色，導向 `/about/`。
6. **合作邀請**：單一清楚的聯絡入口，導向 `/contact/`。

V1 移除地方筆記區塊後，不以新段落填補版面，也不把案例或關於全文搬回首頁。精煉依靠編輯、層級、節奏與留白，不靠縮小字體或壓縮段距。

### 5.2 關於我們：品牌與人的工作現場

關於頁使用「工作桌」的敘事方式，回答：

- 品牌為何成立、為何從屏東出發。
- 公司／團隊在合作中的角色。
- 如何理解地方、品牌、企業與公共資源之間的工作。
- 團隊、人物及自有品牌之間的關係；只有已核實內容可公開。
- 導向合作方式與聯絡頁的下一步。

這一頁不負責列出所有案例，也不把未核准的理念提案當成正式品牌宣言。

### 5.3 合作方式：把能力轉成可理解的合作情境

合作方式頁回答「何時適合找屏方根」與「合作如何發生」，至少分清：

- 合作情境與可處理的問題。
- 工作範圍與不包含的事項。
- 從理解需求、共同判斷到交付的基本流程。
- 可佐證的方法或案例連結。
- 必要 FAQ 與聯絡入口。

文案不得承諾尚未確認的服務、時程、成果或政府資源媒合結果。

### 5.4 合作案例：證明工作如何發生

案例索引使用「流域索引」的資訊組織方式，但第一版不為了形式加入大型篩選器。內容量少時，以清楚的序列與分類文字即可。

每則案例內頁的建議結構：

1. 已核准的案例名稱與一句摘要。
2. 背景與真實需求。
3. 關鍵判斷與工作方法。
4. 屏方根、客戶、夥伴各自的角色。
5. 過程、材料或現場紀錄。
6. 可核實的成果；沒有資料時不自行推論成效。
7. 回顧與延伸合作入口。

同一段內容不在首頁、案例索引與案例內頁重複展開：首頁是線索，索引是比較與選擇，內頁才是完整敘事。

### 5.5 聯絡：真實可完成的下一步

V1 優先提供已驗證的電子郵件或其他正式管道。若表單尚未接收、驗證及通知，production 不顯示可送出的假表單。

聯絡頁需清楚說明：

- 適合提出哪些合作需求。
- 建議來信包含哪些基本資訊。
- 個人資料用途與回覆安排。
- 實際可用的送出方式及成功／失敗狀態。

登入、會員、資料庫、商城、訂閱與搜尋不在 V1 範圍。

## 6. 內容來源與權限

| 內容類型 | 主要來源 | 網站使用規則 |
| --- | --- | --- |
| 品牌事實與決策 | Dokki 有效決策文件 | 僅使用標示為有效且可公開的版本；提案不可冒充定案 |
| CI、Logo、字體與色彩 | Dokki／原始品牌檔案 | 必須使用核對過的正式資產；概念圖形不等於正式 Logo |
| 案例事實 | Dokki 案例資料卡、客戶／品牌確認 | 名稱、角色、成果、夥伴、引言、圖片逐項確認公開權限 |
| 既有活動內容 | `0605/events/mangzhong-2026-0605/` | 以現行 production 為回歸基線，不由品牌站概念稿覆寫 |
| 聯絡資訊 | 專案擁有者確認 | 上線前實際測試，不使用占位信箱或示意成功訊息 |
| 影像與署名 | 正式攝影／品牌提供並附權利資訊 | AI 概念圖不得冒充真實人物、場域或案例證據 |
| 版面與敘事參考 | A／B／C 設計留存與整合預覽 | 可作設計依據，不作品牌事實來源 |

內容狀態至少區分：`草稿`、`待核准`、`可公開`、`已發布`、`撤下`。只有「可公開」或「已發布」可進入 production；網站實作者不得自行提升狀態。

## 7. V1 技術與發布邊界

- 部署輸出仍以 `0605/` 為單一 Cloudflare Pages 根目錄。
- 品牌頁、共用 CSS／JS／資產與既有 `events/` 必須同時存在於同一部署包。
- V1 為靜態多頁網站；不因未來 Dokki 整合而先加入前端 API 呼叫。
- production 不包含設計說明、內部文件、SHA 清單、概念稿標示或未核准頁面。
- preview 全站 `noindex,nofollow`；production 的 robots、canonical、Open Graph、sitemap 與必要 JSON-LD 只涵蓋已核准公開路由。
- 移除根路徑導向活動頁的暫時 302 後，仍保留活動頁本身的正規化規則。
- 不存在的路徑回傳品牌化 404，不把所有錯誤重寫到首頁。

## 8. V1.1：地方筆記與 Dokki 邊界

### 8.1 地方筆記的啟用條件

V1.1 才加入 `/journal/` 與 `/journal/[slug]/`。啟用前至少需要：

- 一組可公開且已完成編輯的文章，而不是示意標題或「編輯試稿」。
- 每篇都有唯一 slug、摘要、正文、作者、發布／更新日期、主題、封面或內文圖片、替代文字、署名／授權、SEO 欄位與發布狀態。
- 索引、文章、返回路徑、相關案例與 404 行為完成驗證。
- 首頁只加入少量精選入口，不把文章全文搬進首頁。

Journal 上線時才加入主導覽、footer 與 sitemap。在此之前，V1 不放「即將推出」的空頁面。

### 8.2 Dokki 的角色

Dokki 在 V1 與 V1.1 都是內容與決策的主檔；網站只呈現核准的公開版本。V1.1 可以先以人工審核後的靜態輸出發布 Journal，不必等待自動同步。

若要加入自動同步，必須先證實 Dokki 有穩定、允許正式網站使用的讀取／發布介面，並完成以下映射與行為：

- 公開狀態、slug、標題、摘要、正文、作者、日期、圖片與 SEO 欄位。
- 新增、更新、撤稿、slug 變更、資產失效、同步失敗與快取更新。
- 預覽與 production 的內容隔離。
- 編輯核准與網站發布紀錄可追溯。

同步應在受控的建置或伺服器端流程執行；Dokki／MCP 憑證不得進入前端 JavaScript。若介面或錯誤處理尚未成熟，維持人工核准、靜態發布，不另建一套人工重複編輯正文的後台。

## 9. V1 完成定義

V1 可進入 production 的條件是：

- 首頁、關於、合作方式、案例索引、所有公開案例與聯絡頁可直接開啟及重新整理。
- 地方筆記不在部署輸出、導覽、footer 或 sitemap 中。
- 根網址顯示品牌首頁；既有活動頁原網址、素材、互動與報名入口正常。
- 所有公開文字、圖片、人物、案例與聯絡方式均有來源及核准狀態。
- 沒有 AI 圖像冒充紀錄、占位事實、假成功表單或內部開發說明。
- 手機與桌面可閱讀，鍵盤焦點與減少動態設定可用，無斷鏈或缺失資產。
- preview 維持 noindex；production 的搜尋資訊僅涵蓋核准頁面。
- Git 提交、Cloudflare deployment、正式版本與回滾點均有紀錄。

## 10. 後續實作分工依據

程式整合工作以本文件的路由與發布清單為準；內容整理工作以 Dokki 的公開狀態與核准清單為準。兩者可以平行：

- 程式端先建立 V1 路由、共用元件／資產、Cloudflare 特殊檔案與既有活動頁回歸保護。
- 內容端同步整理品牌、服務、案例與聯絡資料的來源和公開權限。
- 未核准內容不阻塞路由骨架與本機驗證，但必須阻塞該內容進入 production。
- 地方筆記與 Dokki 自動同步屬 V1.1，不應阻塞 V1 主站。

本文件只定義 V1 的網站架構與內容邊界，不修改 `0605/` 任何程式或部署設定。
